# 企业服务台 Agent 业务规则表

这份表是给产品经理维护业务规则用的版本。它不要求 PM 直接写 JSON，而是把当前代码配置里的规则翻译成产品口径：

> 员工问什么问题 → 属于哪类业务 → 需要哪些信息 → 默认怎么处理 → 什么情况升级 → 最终给员工什么结果。

对应代码配置来源：

- 服务范围、问题分类、典型问法：`config/intent-rules.json`
- 每类问题的处理套路：`config/agent-skills.json`
- 风险升级规则：`config/risk-rules.json`
- 可执行动作：`config/tool-registry.json`

## 1. 服务范围规则

| 输入类型 | 示例 | 是否进入业务处理 | 处理方式 | 是否建单 | 是否记录知识缺口 |
| --- | --- | --- | --- | --- | --- |
| 有效企业服务请求 | “帮我申请 VPN 权限”“年假还剩几天”“报销 1200 元” | 是 | 进入意图识别和业务流程 | 视问题类型决定 | 视知识库命中情况决定 |
| 闲聊/打招呼 | “你好”“在吗”“谢谢”“再见” | 否 | 直接轻量回复 | 否 | 否 |
| 无实义输入 | “？？？”“……” | 否 | 提示员工说具体一点 | 否 | 否 |
| 域外请求 | “今天天气怎么样”“帮我写代码”“股票涨了吗”“午饭吃什么” | 否 | 说明不在企业服务台范围 | 否 | 否 |
| 非本公司事务 | “帮我投外面的岗位”“其他公司怎么报销” | 否 | 说明只处理本公司内部事务 | 否 | 否 |

产品规则：

- 闲聊和域外请求必须在业务流程前拦截。
- 域外请求不算知识库缺失，因为公司不会为天气、股票、写代码准备内部制度。
- 只有 IT、HR、财务、行政相关问题才进入后续处理。

## 4. 必填信息与追问规则

| 场景 | 必填信息 | 能否缺失后继续办理 | 缺失时追问 |
| --- | --- | --- | --- |
| 软件安装 / 授权申请 | 软件名称 | 否 | “你要申请哪个软件？” |
| 生产数据 / 高权限访问 | 目标系统 | 否 | “你要申请哪个系统或环境的权限？” |
| 请假 / 调休申请 | 假期类型、开始日期、天数 | 否 | “请补充假期类型、开始日期和请假天数。” |
| 提交报销单 | 报销金额 | 否 | “这笔报销金额是多少？” |
| 预算 / 付款审批 | 金额 | 否 | “请补充付款或预算金额。” |
| 会议室 / 场地 | 无必填；日期、人数可选 | 是 | 不强制追问，可根据制度给预定方式 |
| 出差 / 订票 | 无必填；城市、日期可选 | 是 | 不强制追问，可先说明流程 |
| 办公用品领用 | 无必填；物品可选 | 是 | 不强制追问，可先说明领用规则 |

产品规则：

- 关键字段缺失时，优先追问，不创建业务工单。
- 可选字段缺失时，可以继续给制度指引。
- “追问”本身不代表转人工，也不代表失败。

| 必填信息缺失 | 强制追问 | 不创建业务工单 |

## 6. 知识库缺失定义

知识库缺失不是“没有搜到一模一样的问题”，而是：

> 当前知识库无法提供足够可靠的制度依据，支撑 Agent 对员工问题做出明确回答或办理判断。

| 情况 | 是否算知识库缺失 | 处理方式 |
| --- | --- | --- |
| 完全没有检索到相关制度 | 是 | 记录知识缺口，转人工 |
| 搜到的制度和问题不是同一类业务 | 是 | 不引用，记录知识缺口 |
| 搜到的内容太泛，无法回答具体问题 | 是 | 不直接回答，转人工 |
| 制度缺关键条件，例如金额上限、适用范围、审批链路 | 是 | 转人工确认 |
| 多份制度相互冲突 | 是 | 转人工确认 |
| 制度明显过期 | 是 | 转人工确认或提示需人工核实 |
| 员工问天气、写代码、股票、午饭推荐 | 否 | 这是域外请求，不记录知识缺口 |
| 薪酬、绩效、离职等敏感事项 | 不一定 | 按敏感事项流程转 HRBP，不在聊天展开 |

产品规则：

- 没有可靠依据时，Agent 不能用“通常来说”“一般可以”补答案。
- 只有服务范围内的问题，才可能进入知识缺口。
- 知识缺口需要记录问题原文、所属领域、识别到的意图、最高相似度和出现次数。

## 7. 工具动作定义

| 动作 | 业务含义 | 什么时候触发 |
| --- | --- | --- |
| 查知识库 | 找制度依据 | 大多数制度问答和办理流程 |
| 查员工信息 | 获取员工部门、职级、状态、上级、年假等 | HR 问答、请假、报销、权限等 |
| 查权限状态 | 看员工是否已有某系统权限、权限是否过期 | VPN、软件授权、生产权限 |
| 创建工单 | 把需要落地处理的事项交给对应团队 | 中风险办理事项、高风险事项、兜底转人工 |
| 创建人工确认任务 | 让人工确认是否能执行 | 生产权限、大额资金、薪酬离职、长假等 |
| 记录知识缺口 | 把答不上来的服务台问题沉淀给知识运营 | 服务范围内但知识库无可靠依据 |
| 转人工 | 明确后续由人工团队接手 | 高风险、无依据、无法识别但像公司事务 |

## 8. 员工结果展示规则

| 处理结果 | 员工看到的内容 |
| --- | --- |
| 直接回答 | 答案正文 + 制度依据 |
| 追问补充 | 已识别的事项 + 缺少哪些信息 + 需要员工补充什么 |
| 创建工单 | 处理说明 + 工单号 + 负责团队 + 预计响应时间 |

| 知识库无依据 | 明确说明没有可靠制度依据 + 已记录知识缺口 + 已转人工 |
| 域外请求 | 说明不在服务台范围 + 可处理的服务范围 |

PM 不需要直接改 JSON，建议维护下面这张业务表，再由工程或配置后台同步到底层配置。

| 维护项 | PM 需要提供什么 |
| --- | --- |
| 新增问题类型 | 问题名称、所属部门、典型问法、反例 |
| 新增处理流程 | 默认动作、负责团队、是否需要制度依据、员工话术 |
| 新增必填字段 | 字段名称、是否必填、缺失时怎么追问 |
| 新增风险规则 | 触发条件、风险等级、是否人工确认、转交团队 |
| 调整知识库标准 | 什么情况下允许回答，什么情况下必须转人工 |
| 验收用例 | 输入样例、预期识别类型、预期动作、预期员工结果 |

推荐的维护节奏：

1. 从后台日志看高频问题和知识缺口。
2. 挑选高频且流程明确的问题沉淀为新意图。
3. 对涉及权限、资金、人事敏感的问题补充强风险规则。
4. 每次新增规则都补充正向样例和反例，避免误判。
