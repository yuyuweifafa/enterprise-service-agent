# 企业内部服务智能体（Enterprise Service Agent）

面向员工的 **IT / HR / 财务 / 行政 一站式智能服务台**。

不是又一个 RAG 问答 Demo。这套系统要回答的是一个更实际的问题：**企业内部服务台的 Agent，凭什么敢真的上线？**

答案是四件事：多意图拆解、每句话都能追溯到制度条款、按风险分级决定"自动做"还是"交给人"、以及答不上来时如实说不知道并把问题沉淀下来。

> **默认零配置可跑**：不需要任何 API Key，`npm install && npm run dev` 就是完整可演示的规则引擎版本。
> **也支持真实大模型**：配三个环境变量即可切到智谱 GLM（或任何 OpenAI 兼容供应商），见[双引擎架构](#双引擎架构mock--llm)。

## 它解决什么问题

企业内部服务台的典型现状：员工问题 60% 是重复的制度咨询，服务台被这些问题淹没；剩下 40% 里混着必须谨慎处理的高风险请求（生产数据库权限、大额付款、离职）。

传统做法两头都不讨好：

| 做法 | 问题 |
| --- | --- |
| 纯人工服务台 | 重复问题消耗人力，首响平均 47 分钟 |
| 纯 FAQ 机器人 | 只能答不能办，答不上来就死路一条 |
| 纯 RAG 问答 | 会编答案；不区分"告诉你年假几天"和"给你开生产库权限" |

这套系统的取舍是：**能自动办的直接办完，不能自动办的把人工需要的判断材料准备好**。

## 核心能力

系统分两侧，面向不同角色、不同权限：

| 侧 | 路由 | 使用者 |
| --- | --- | --- |
| **员工端** | `/chat` | 全体员工。界面极简，只有一个输入框和处理结果侧栏。 |
| **服务台后台** | `/console/*` | 服务台同事（IT / HR / 财务 / 行政 / 安全）。工单、审核、知识、度量四个模块。 |

`/` 是演示用的入口页，显式展示两侧的角色边界。真实环境里员工登录后直接落到 `/chat`，看不到后台入口。

| 能力 | 说明 | 在哪看 |
| --- | --- | --- |
| **多意图识别** | 一句话拆出多个独立诉求，各自走完整流程 | 员工端侧栏「意图识别与处理明细」 |
| **知识库引用** | 回复中的每条结论都标注`文档编号 + 章节`与相似度分数 | 员工端侧栏「知识库引用来源」 |
| **风险分级** | LOW 自动答复 / MEDIUM 自动建单 / HIGH 人工确认，规则可配置且命中原因可见 | 员工端侧栏「风险分级依据」 |
| **工具调用** | 按 Skill 配置调用 mock API（查档案、查权限、建单、建审批），入参与耗时全留痕 | 员工端侧栏「工具调用明细」 |
| **工单生成** | 自动路由到职能团队、按风险定 SLA，并带上 Agent 当时的引用与抽取信息 | 后台 · 工单中心 |
| **人机协同** | 高风险事项 Agent 只给建议不执行，人工确认 / 驳回 / 接管，决策回写工单时间线 | 后台 · 人工审核台 |
| **未命中沉淀** | 检索不到依据时如实说明 + 记录待补充知识（相似问题累加次数）+ 转人工 | 后台 · 知识运营 |
| **槽位追问** | 关键信息缺失时先问清楚，而不是先建一张错单 | 员工端场景 ⑥ |
| **闲聊前置拦截** | 「你好」「谢谢」「？？？」这类输入直接轻量回复，不检索、不建单、不沉淀、不调大模型 | 员工端输入「你好」 |
| **域外请求识别** | 天气、写代码、点餐这类不属于服务台职责的请求，说明服务范围并引导，**不算知识缺口** | 员工端输入「今天天气怎么样」 |
| **效果看板** | 解决率 / 命中率 / 转人工率 / 响应时间 / 节省工时，口径全部写明 | 后台 · 效果看板 |

## 快速开始

前置：**Node.js ≥ 18.18**（推荐 20 LTS）。项目附带 `.nvmrc`。

```bash
nvm use            # 可选，切到 Node 20
npm install
npm run dev
```

打开 <http://localhost:3000> 即可。**不需要配置任何环境变量或 API Key。**

首次请求时会自动把 `data/seed/` 复制到 `data/runtime/` 作为可写数据。演示前想恢复初始状态：

```bash
npm run seed:reset
```

其他命令：

```bash
npm run build           # 生产构建
npm run typecheck       # TypeScript 全量类型检查
npm run lint            # ESLint
npm run smoke           # 端到端冒烟测试（需先起 dev server，125 项断言）
npm run eval:retrieval  # 检索质量回归（27 条样例，含"应未命中"样例）
npm run eval:threshold  # 相似度阈值扫描，给出建议阈值

npm run llm:fake        # 启动本地假大模型服务（OpenAI 兼容），用于无 Key 验证 LLM 链路
npm run dev:llm-fake    # 以 llm 引擎启动应用，指向上面的假服务
npm run smoke:llm       # LLM 路径专项测试（54 项断言，含 6 种故障降级场景）
npm run llm:models      # 用你的 Key 列出供应商实际可用的模型名
```

> ⚠️ 不要在 dev server 运行时执行 `npm run build` —— 两者共用 `.next` 目录，
> 生产构建会覆盖 dev 的 chunk，导致 `Cannot find module './xxx.js'`。
> 真遇到了：`rm -rf .next && npm run dev`。

## 双引擎架构：mock 与 llm

同一套六段式管线，两种引擎共用，差别只在**两段**的实现：

| 管线阶段 | `mock` 引擎 | `llm` 引擎 |
| --- | --- | --- |
| 1. 多意图识别 + 槽位抽取 | 关键词 / 正则 / 否定词打分 | **function calling 结构化输出** |
| 2. 知识检索 | 字段加权 TF-IDF | 同左（向量检索是下一步） |
| 3. 读取类工具调用 | Skill 配置驱动 | 同左 |
| 4. 风险分级 | **12 条规则** | **同左，模型无权干预** |
| 5. 动作编排与写入工具 | **规则 + Skill 配置** | **同左，模型无权干预** |
| 6. 回复合成 | Skill 模板拼装 | **System Prompt + 检索片段驱动生成** |

### 为什么风险分级不交给模型

这是整个设计里最重要的一条取舍。

员工问「这笔 8600 的报销能不能提」，答错的代价是真实的。规则引擎能回答「因为命中 R005，报销金额 ≥ 5000 元，所以转人工复核」——**可审计、可回归测试、可向合规解释**。让模型自己决定要不要开生产库权限，出问题时无法定位是哪一步错了，也没法写测试防止下次再错。

所以 `llm` 引擎下，模型拿到的是「已经定好的结论」，只负责把它说清楚：

```
风险判定（已由规则引擎确定，不可更改）：HIGH —— 人工确认
命中规则：R001 生产环境与高权限关键词；R009 试用期员工的权限申请
系统已经执行的动作（如实告知员工，不要多说也不要少说）：
- 已创建工单 TK-20260826-0011，处理团队 安全与合规组，1 小时内响应
- 已创建人工确认任务 AP-20260826-0005。Agent 没有执行、也不会自动执行该操作。
```

### 三道防线：模型输出不可信

`src/agent/llm/intent.ts` 里对模型输出做三层校验：

1. **意图白名单**：模型返回配置里不存在的 intent id 一律丢弃。否则下游的 Skill、风险规则、工单路由都没有对应配置。
2. **槽位类型强制转换与拒绝**：`"8600元"` → `8600`；不在枚举内的值直接拒绝而不是硬塞。被拒的值会写进处理链路，界面上能看到。
3. **规则抽取器兜底**：最终槽位 = 规则抽取 ∪ 模型抽取（模型优先）。日期、金额这类结构化信息正则比模型稳，模型漏抽时不至于退化成追问。

代码校验之外还有一条 prompt 层的防护：**模型倾向硬套最接近的意图，而不是承认不匹配**（实测那次它给了 0.8 的置信度）。`config/intent-prompt.md` 里因此加了判断标准和两个反例——判断依据是「这个意图对应的制度文档能不能直接回答这个问题」，而不是「有没有共同关键词」。

### 降级绝不说谎

这是我特意加固的一点。三种情形分得很清：

| 情形 | 行为 |
| --- | --- |
| `AGENT_ENGINE=llm` 但缺 API Key | **启动直接失败**并打印所需配置。不静默退回规则。 |
| 运行期单次调用失败（限流/超时/5xx/脏响应/空回复） | 降级到规则引擎保证可用，但 `engine` 字段标回 `mock`、`degraded=true`、`degradedReason` 写明错误码与重试次数，界面顶部显示黄色降级提示 |
| 模型说「没有匹配的意图」 | 这是**业务结论**，走兜底 Skill（如实告知 + 沉淀知识缺口 + 转人工），不算故障 |

第三条和第二条的区分是被测试逼出来的：最初的实现把「模型返回空/无法解析」也当成了「员工诉求无法识别」，结果模型抽一次风，就会给员工凭空建一张工单 + 记一条知识缺口。现在解析失败会抛 `LlmIntentParseError` 触发降级，只有模型明确返回合法结构且无匹配时才走兜底。

### 智谱各模型实测（2026-08，同一个 Key、同一体量 prompt）

选模型不能只看单价。下面是接入后实测的数据：

| 模型 | 档位 | 单次调用延迟 | 稳定性 |
| --- | --- | --- | --- |
| `glm-4.7-flash` | 免费 | 19 ~ 27 s | 频繁 `429 该模型当前访问量过大` |
| `glm-4.5-flash` | 免费 | 20 ~ 21 s | 同上 |
| **`glm-4.5-air`** | 付费 | **1.8 ~ 3.5 s** | 稳定（**推荐**） |
| `glm-4.7` | 付费 | 1.5 ~ 3.3 s | 稳定，质量更好 |

**结论：免费 Flash 档不适合交互式服务台。** 免费不是价格问题而是排队问题——一次对话要 2 次模型调用，叠起来 40 秒以上，演示时看着像卡死。付费档换算下来一次对话约两分钱，Demo 量级可以忽略。

两个实测得出的优化，都已经落进配置：

- **关闭思考模式**：`config/app.config.json` 的 `llm.extraBody` 默认带 `{"thinking":{"type":"disabled"}}`。服务台不需要模型长篇推理，关掉后延迟差好几倍。换非智谱供应商时把这里改成 `{}`。
- **级联意图识别**：`llm.intentStrategy` 默认 `rules-first-escalate` —— 先跑规则引擎（约 1ms、0 成本），置信度 ≥ `intentEscalationThreshold`（默认 0.7）就直接用，不够才升级到大模型。「OA 密码忘了」这种明确表述，正则和大模型一样准，没必要花几秒让模型再确认一遍。**省一次调用 = 省一半延迟和一半 token**。

超时默认 20 秒也是刻意的：服务台场景宁可快速降级到规则引擎给员工一个立即可用的答复，也不要让人对着转圈等 45 秒。

### 接智谱（推荐 `glm-4.5-air`）

```bash
cp .env.example .env.local
# 编辑 .env.local：
#   AGENT_ENGINE=llm
#   LLM_BASE_URL=https://open.bigmodel.cn/api/paas/v4
#   LLM_API_KEY=<在 bigmodel.cn 控制台创建>
#   LLM_MODEL=glm-4.5-air
npm run dev
```

> `npm run llm:models` 可以列出模型，但**这个端点的清单不完整**——实测 `glm-4.7-flash` 能正常调用却不在列表里。
> 拿不准就直接发一个最小请求试，或去控制台的模型页确认。

换供应商只改 `LLM_BASE_URL` / `LLM_MODEL` 两行，代码不动。`.env.example` 里附了 DeepSeek / 通义 / Moonshot / 本地 Ollama 的配置示例。

### 没有 API Key 也能验证 LLM 链路

`scripts/fake-llm-server.mjs` 是一个本地的 OpenAI 兼容假服务，能返回结构化的 function calling 响应，还能按需注入 6 种故障（`429` / `401` / `500` / 响应非 JSON / 空回复 / 超时）。

```bash
# 终端 1
npm run llm:fake
# 终端 2
npm run dev:llm-fake
# 终端 3
npm run smoke:llm     # 54 项断言
```

这套东西存在的意义：**LLM 集成代码在交付前是真的跑过的**，而不是一堆看起来对但没验证过的代码。也让 CI 能在不花钱、不依赖外部服务的前提下守住这条链路。

## Demo 演示流程（六条路径）

对话页顶部有六个一键按钮，按顺序点一遍就是一次完整演示。每条路径都在验证一个不同的设计决策。

### ① 低风险 · 直接答复

> 出差去成都，住宿一晚最多能报多少钱？

`FINANCE / fin.reimburse_policy` → 风险 **LOW** → 直接引用《费用报销管理制度》「差旅标准」回答，不建单。
**看点**：回复里带出了具体金额表格与来源章节，同时补上了"你的办公地/成本中心/审批人"——这些是查 mock 员工档案得到的，不是编的。

### ② 多意图 · 一句话两件事

> OA 密码忘了怎么重置？另外我 9 月 7 日想请 3 天年假

拆成两个意图：`IT / it.password_reset`（LOW，自助指引）+ `HR / hr.leave_apply`（MEDIUM，建单）。
**看点**：两个诉求各自独立完成检索、风险判定与动作，互不干扰。请假意图还抽出了 `startDate=2026-09-07`、`days=3`——注意"9 月 7 日"里的"7 日"没有被误判成天数。

### ③ 中风险 · 自动建单

> 我的笔记本这两天一直蓝屏，帮我报修一下

`IT / it.device_repair` → **MEDIUM** → 先给自查步骤，同时自动创建 P2 工单路由到 IT 桌面运维。
**看点**：去工单中心展开这张单，Agent 当时引用的制度章节和抽取的槽位都在里面——人工接手不用再问一遍。

### ④ 高风险 · 人工确认（用试用期员工演示）

顶部把当前员工切成 **E1003 陈可（试用期）**，然后：

> 帮我开通生产数据库的只读权限，我要查订单表

`IT / it.data_permission` → **HIGH**，命中两条规则：

- `R001` 生产环境与高权限关键词 → 置为 HIGH
- `R009` 试用期员工的权限申请 → 上调 1 级

**看点**：Agent 明确回复"我不能直接开通"，同时创建工单 + 人工确认任务。去人工审核台看这条任务，里面已经准备好了人工需要的全部判断材料：命中的风险规则、引用的制度条款、员工档案快照、以及"Agent 查过哪些系统"（生产数据库权限现状 = NONE）。建议动作里还给了替代方案——改授数仓脱敏视图。点「驳回」，回到工单中心看状态和时间线已同步。

> 把员工换成 E1001（正式员工）再问一次，会看到只命中 R001、少了 R009。这就是风险规则可配置的意义。

### ⑤ 未命中 · 知识沉淀

> 下个月带样机去德国参展，海关清关手续怎么办？

知识库最高分 0.16 < 阈值 0.20 → 判定未命中。
**看点**：Agent 没有硬凑一个答案，而是明确说"没有找到明确的制度依据"，同时沉淀知识缺口 + 转人工。去知识运营页能看到这条缺口，**且出现次数是累加的**（相似问法不会重复建条目），可以推进为「拟稿中」。这条路径是这类系统能不能长期用下去的关键。

### ⑥ 槽位缺失 · 主动追问

> 帮我提交一笔报销

识别为 `fin.reimburse_submit`，但必填槽位 `amount` 缺失 → 规则 `R012` 强制动作为 `clarify`。
**看点**：Agent 追问金额，**不建单**。对比一下：如果不做这一步，系统会生成一张金额为空的废单，反而增加人工工作量。

### 补充：金额触发风险升级

> 帮我提交一笔 8600 元的差旅报销

抽出 `amount=8600` → 命中 `R005`（报销 ≥ 5000 元）→ 从 MEDIUM 升到 **HIGH**。演示"风险等级由数据决定，不是由意图决定"。

### 最后看看板

聊完这几轮，去 `/console/dashboard` 刷新——今天的会话量、解决率、转人工率、平均响应时间都变了。**看板不是静态图片，是从你刚才产生的真实处理日志里算出来的。**

> 演示动线上注意角色切换：前六个场景都在**员工端**（`/chat`）完成，
> 然后从侧栏的深链或顶部按钮切到**服务台后台**（`/console/*`）看工单、审核、知识缺口和看板。
> 这个来回本身就是在演示「同一件事在两个角色眼里是什么样」。

## 技术选型与理由

| 层 | 选型 | 为什么 |
| --- | --- | --- |
| 框架 | **Next.js 15（App Router）** | 前后端同仓、同语言、同类型。API Route 直接就是 mock 后端，不用起第二个服务、不用配 CORS。个人项目里这是最省心的选择，也方便一键部署到 Vercel。 |
| 语言 | **TypeScript（strict）** | Agent 的输出结构（意图/引用/风险/动作）是这个项目的核心契约。类型定义集中在 `src/lib/types.ts`，前后端共用一份，改契约时编译器会告诉你哪里漏了。 |
| UI | **React 19 + Tailwind CSS 3** | 亮色主题，配色走「CSS 变量 + 语义 token」两层：变量定义在 `globals.css` 的 `:root`，组件里只写 `text-ink-muted` / `bg-surface-2` 这类语义类，**换整套配色只改一个文件**。图表**手写 SVG**（`src/components/charts.tsx`），不引图表库：只需要 4 种图形，自己画能完全控制配色与无障碍属性，且零打包体积。 |
| 数据 | **本地 JSON 文件 + Markdown** | 第一阶段最重要的是"clone 下来就能跑"。JSON 零依赖、零 native 编译（不像 better-sqlite3 需要编译工具链）、diff 可读，改一条 mock 数据在 PR 里一眼能看出来。所有读写都收在 `src/server/store.ts` 一层，换 SQLite / Prisma / 真实企业接口时只改 Repository 实现。 |
| 知识库 | **Markdown + frontmatter** | 知识内容应该能被 Git 管理、能 review、能看 diff。往 `knowledge/` 丢一个 `.md` 就会被索引，不需要跑导入脚本、不需要建库。 |
| 检索 | **字段加权 TF-IDF（中文二元组切分）** | 零依赖、零冷启动、**打分过程可解释**。相似度分数和命中字段都能在界面上看到，调参之后能立刻验证效果。数据契约（片段 + 来源标识 + 分数）与真实向量库一致，换 embedding 检索时上层不用改。 |
| 校验 | **Zod** | API 入参校验与 TypeScript 类型同一份声明，错误响应结构统一。 |
| 状态 | **React 内置 + Context** | 页面级数据用 `useState`/`useEffect` 直接打 API 就够了，引 Redux/Zustand 属于过度设计。 |

**没有选 SQLite 的原因**：`better-sqlite3` 需要 native 编译，在部分环境（不同 Node 版本、Windows 无构建工具、Vercel 边缘运行时）会安装失败。对一个要给别人 clone 演示的项目，这个风险不值得承担。Repository 层已经抽象好了，真要换是局部改动。

### 配色与可访问性

`src/app/globals.css` 的 `:root` 是全站配色的唯一入口。文字分四级（`ink` 标题 / `ink-soft` 正文 / `ink-muted` 标签 / `ink-faint` 元信息），标签芯片统一用「浅底 50 + 深字 700 + 中等边框 300」三件套。

| `ink-soft` 正文 | 10.35:1 | 9.65:1 | 9.40:1 |
| `ink-muted` 标签 | 7.58:1 | 7.07:1 | 6.88:1 |

## Agent 处理管线

`src/agent/pipeline.ts` 是固定的六段式流程，**每一段都往 `trace` 里写一条记录**，对话页侧栏直接渲染这个 trace。

```
0. 前置过滤    闲聊 + 域外请求直接轻量回复，不进主管线（省一次模型调用）
1. 意图识别    按连接词（另外/顺便/还有…）切片 → 逐片段打分 → 去重 → 截断到 3 个
2. 槽位抽取    金额 / 日期（含相对日期）/ 天数 / 人数 / 枚举 / 词典
3. 知识检索    按意图所属职能域检索，跨域降权；命中不足阈值即判未命中
3.5 读取工具   由 Skill.tools 里 sideEffect=read 的工具驱动（查档案 / 查权限）
4. 风险分级    Skill 基线 → 顺序评估 12 条规则 → 最终等级 + 命中原因 + 强制动作
5. 动作编排    风险等级动作集 ∪ Skill 默认动作集，按依赖顺序执行写入工具
6. 回复合成    引用片段 + 员工档案事实 + Skill 回复骨架
7. 落日志      写 agent-logs，看板指标从这里汇总
```

**为什么把流程写死，而不是让大模型自由决策？**

企业内部服务场景要的是可审计、可解释、可回归测试。一个员工问"我能不能报这笔钱"，回答错了要能查出是哪条制度、哪条规则导致的。让模型自由编排工具链在 Demo 里很酷，但出问题时无法定位。

后续接大模型替换的是**每一段内部的实现**（意图识别、检索、回复生成），而不是这个骨架。

### 动作集为什么取并集

```ts
actions = 风险等级对应的动作集 ∪ Skill 声明的默认动作集
```

风险规则负责"这件事至少要做到什么强度"，Skill 负责"这类诉求本来就该做什么"。两者都不能被绕过——否则改一个配置就可能悄悄放过一个高风险动作。唯一的例外是 `clarify`（槽位缺失强制追问），它会短路后续动作，避免生成信息不全的废单。

## 风险分级机制

三档策略（`config/risk-rules.json`）：

| 等级 | 策略 | 动作集 |
| --- | --- | --- |
| **LOW** | 自动答复 | `answer` |
| **MEDIUM** | 自动建单 | `answer` + `create_ticket` |
| **HIGH** | 人工确认 | `answer` + `create_ticket` + `create_approval` + `handoff` |

判定流程：**Skill 基线等级 → 顺序评估规则 → 命中则按 effect 调整并记录原因**。

`effect` 支持四种：`setLevel`（直接置为）、`minLevel`（不低于）、`escalate`（上调 N 级）、`forceAction`（强制动作）。

内置 12 条规则：

| 规则 | 触发条件 | 效果 |
| --- | --- | --- |
| R001 | 生产环境 / root / sudo / 堡垒机等关键词 | → HIGH |
| R002 | 批量导出 / 客户名单 / 全量数据 | → HIGH |
| R003 | 意图为薪酬咨询或离职 | → HIGH |
| R004 | 裁员 / 劳动仲裁 / 赔偿金 | → HIGH |
| R005 | 报销金额 ≥ 5000 元 | → HIGH |
| R006 | 预算 / 付款审批类意图 | → HIGH |
| R007 | 任意金额 ≥ 50000 元（兜底） | → HIGH |
| R008 | 连续请假 ≥ 10 天 | → HIGH |
| R009 | 试用期员工申请系统权限 | 上调 1 级 |
| R010 | 知识库未命中 | 不低于 MEDIUM |
| R011 | 意图置信度 < 0.35 | 不低于 MEDIUM |
| R012 | 必填槽位缺失（且当前不是 HIGH） | 强制 `clarify` |

**R012 为什么要加"当前不是 HIGH"这个前置条件**：否则一个高风险请求只要信息填不全，就会被降级成"追问"而绕过人工审批。这是设计规则引擎时最容易踩的坑——规则的执行顺序和作用范围必须显式声明。

新增规则只改 JSON，条件字段见 `src/agent/risk.ts` 的 `evaluateCondition`：
`keywordsAny` / `intentIn` / `domainIn` / `skillIn` / `employeeStatusIn` / `amountGte` / `daysGte` / `confidenceLt` / `noKnowledgeHit` / `missingRequiredSlot` / `currentLevelIn`。

## 知识检索与未命中沉淀

### 检索打分

```
score = [ 章节级信号 + docBonusRatio × 文档级信号 ] / 归一化分母
        × 职能域系数
        × （只命中正文时的降权）
```

- **章节级信号**：二级标题（权重 3）、正文（权重 2，TF 饱和）
- **文档级信号**：文档标题、frontmatter `keywords`（2.4）、`tags`（1.6），按 `docBonusRatio=0.35` 折算
- **每个词取"命中字段的最高权重"而不是求和**
- **归一化分母**：命中词的 IDF 之和 + 知识库里根本不存在的词的代价（按 √数量 增长）
- **职能域系数**：同域 ×1.15，跨域 ×0.55
- **只命中正文降权**：×0.75

调这套参数的过程踩了四个坑，都留在代码注释里了：

1. **字段权重求和** → 一篇文档的所有章节拿到相同分数，引用来源指错章节
2. **只用命中词做归一化** → "整句只有一个词碰巧在知识库里"也能拿到 0.67 的相似度，未命中兜底永远不触发
3. **OOV 惩罚按线性增长** → 问题问得越啰嗦分数越低，正常长句被判成未命中
4. **"公司""员工"这类词没进停用词** → 内部知识库里几乎每篇都有，任何提问都能"蹭"到一点分

修完之后，27 条样例的 Top1 命中率 100%，4 条"应未命中"样例全部正确判定为未命中：

```bash
npm run dev              # 另开终端
npm run eval:retrieval
```

阈值不是拍脑袋定的。`npm run eval:threshold` 会把"应命中"和"应未命中"两组样例的分数打出来，给出建议阈值：

```
应命中的最低分：0.2417
应未命中的最高分：0.1723
两组可分。建议 scoreThreshold = 0.207
```

当前设为 **0.20**。往 `knowledge/` 加文档后重跑一次，就知道阈值要不要调。

### 检索 query 只用员工原话

早期实现把意图配置里的 `knowledgeTags` 拼进检索 query，本意是帮助检索。意图识别正确时没什么收益，**意图识别错误时是灾难**：错误的 tags 会让那篇文档的每个章节都命中 `keywords` 而被推过相似度阈值，`knowledgeHit` 变成 true，于是未命中兜底永远不触发。

实测案例：「带样机去德国参展的清关手续」被误判成出差意图后，Agent 自信地答了订票流程。

修法是检索只用员工原话，并且把 `knowledgeTags` 参数从 `SearchOptions` 上彻底删掉——留着就还会有人拼回去。`scripts/eval-retrieval.mjs` 里 4 条「应未命中」样例守的就是这条路径。

### 三类输入必须分开处理

这是实测踩出来的。主管线的隐含假设是「所有输入都是四个职能域内的服务请求」，于是它总能找到一个"最接近"的意图。真实发生过的三个 bug：

| 输入 | 修复前的行为 |
| --- | --- |
| 今天天气怎么样 | 沉淀知识缺口「今天天气怎么样」+ 转人工，回复「将由内容运营补充相关制度」 |
| 帮我写一段 Python 冒泡排序 | **识别成薪酬咨询 → 判 HIGH → 建工单 + 建人工确认任务** |
| 推荐个附近的午饭 | **识别成办公用品领用**，检索命中 0.2227，自信地答「到一楼行政前台领取」 |

第二个最严重（写代码变成 HRBP 待处理的薪酬事项），第三个最危险（回答看起来完全正常，员工只会觉得系统在胡说）。

根因是缺了中间这一类：

| 输入类型 | 处理方式 | 会不会建单 / 沉淀 |
| --- | --- | --- |
| 闲聊 / 无实义 | 轻量回复 | 都不会 |
| **域外请求**（天气、写代码、点餐） | 说明服务范围 + 引导能力 | **都不会**——公司不会为「天气」写制度 |
| 域内但知识缺失（清关手续、员工持股） | 如实说没依据 | **都会**——这才是真正的知识缺口 |

**换更强的模型解决不了这个问题**：

1. 模型其实是照指令执行的 —— compose prompt 里写着「知识库没有依据就如实说明」，它照做了。指令本身错了，因为它假设「没找到 = 制度缺失」。
2. 副作用是规则驱动的 —— 建单和记缺口由 R010 触发，模型答得再得体，脏数据照样产生。
3. 意图误判无法靠模型质量根除 —— 案例 2、3 是低概率高后果错误，好模型少犯但一旦犯了下游整条链路还是照走。

所以做了两层防御：

- **第一层：规则黑名单**（`config/intent-rules.json` → `outOfScope`）。天气、写代码、通用知识、股价新闻、生活娱乐、非本公司事务六类。1–5ms 拦下，零模型调用。
- **第二层：让模型显式区分**。意图识别的 function schema 加了 `scope` 字段，`unmatched=true` 时必须填 `in_scope` 或 `out_of_scope`。判断方法写在 prompt 里：「公司的制度库里将来有可能出现一篇讲这件事的文档吗？」有 → in_scope，没有 → out_of_scope。这层兜住黑名单没覆盖的问法（实测「我家猫生病了怎么办」「介绍一下量子力学」都被正确判为域外）。

误拦防护：`matchMode: contains` 的词条选得很谨慎，比如没有把「代码」设成关键词 —— 否则「我要申请代码仓库的访问权限」会被误拦。测试里有这条反向断言。

### 顺带修掉的一个隐藏 bug

加固 prompt 后暴露出来的：`tool-registry.json` 把 `ticket.create` 的 `intentId` 声明为必填，但意图未识别时它就是 `null`，于是**兜底路径永远建不出工单**：

```
ticket.create SKIPPED | 缺少必填入参: intentId
```

后果是知识缺口记下了、回复也告诉员工「已转交人工」，但**没有任何工单，没人跟进**。这条正是「未命中沉淀 + 转人工」的核心路径，之前一直是坏的，因为之前模型总能硬套出一个意图（掩盖了这个 bug）。已改为非必填，并在配置里写明了原因。

### 未命中沉淀闭环

```
检索最高分 < 阈值
   ↓
如实告知员工「没有找到明确的制度依据」（不编答案）
   ↓
kb.record_gap → 相似问题累加 occurrences（token 交集 ≥ 60% 判为同一问题）
   ↓
转人工 + 建单跟进
   ↓
知识运营页：待补充 → 拟稿中 → 已发布
   ↓
补写 Markdown → 命中率回升
```

这条闭环决定了系统上线后知识命中率是往上走还是原地踏步。

## 看板指标口径

口径参数全在 `config/app.config.json` 的 `metrics` 段。指标 = **历史聚合（`data/seed/metrics-history.json`）+ 实时日志（`data/runtime/agent-logs.json`）** 按自然日合并。

| 指标 | 口径 |
| --- | --- |
| 自助解决率 | 未转人工的会话 / 总会话 |
| 知识命中率 | 至少检索到 1 条超过相似度阈值片段的会话 / 总会话 |
| 转人工率 | 触发 `handoff` 或判定 HIGH 的会话 / 总会话 |
| 平均响应时间 | 服务端处理耗时，按会话量加权；P90 取自实时日志 |
| 节省工时 | Σ(各域自动解决量 × 该域人工单次处理分钟数) / 60 |
| 节省成本 | 节省工时 × `hourlyCostCNY`（默认 85 元/小时） |
| 人力当量 | 节省工时 / (区间工作日 × 8) |

两个刻意的处理：

1. **口径不变式写进了数据文件**：`autoResolved + escalated = conversations`。一次会话要么 Agent 闭环、要么转人工，没有第三种。所以看板上"解决率 + 转人工率 = 100%"永远成立，冒烟测试里有这条断言。
2. **没有预置任何历史数据**：`data/seed/metrics-history.json` 是空的，看板上每一个数字都来自你实际产生的处理日志。刚 clone 下来看板是空的，聊几句就有了。这样演示时说「这些指标是真实算出来的」才站得住。想要一条好看的趋势线截图，那个文件里写了行结构和口径约束，自己补即可。

3. **闲聊不计入口径**：`metrics.excludeSmallTalkFromMetrics` 默认 true。否则员工说几句「你好」就能把自助解决率刷上去，这个指标就没意义了。被剔除的条数在接口里以 `smallTalkExcluded` 返回，不藏着。

**高风险强制转人工会拉低自助解决率，这是有意为之的取舍**：如果只优化解决率这一个指标，最省事的做法就是把高风险规则删掉。

### Prompt 都写在哪

四处，全部是配置文件，改完刷新页面即生效（开发环境每次请求重读配置）：

| 文件 | 作用 | 生效引擎 |
| --- | --- | --- |
| `config/system-prompt.md` | **全局** System Prompt：角色、六步流程、硬性约束、语气 | `llm` |
| `config/intent-prompt.md` | **意图识别**阶段的 system message。`{{catalog}}` 会被 `intent-rules.json` 生成的意图目录替换，`{{today}}` 换成当天日期 | `llm` |
| `config/agent-skills.json` → `skills[].prompt` | **Skill 级追加指令**：这一类诉求回复时要注意什么，拼在全局 System Prompt 之后 | `llm` |
| `config/agent-skills.json` → `skills[].replyTemplate` | 规则引擎的回复骨架，支持 `{{answer}}` `{{ticketId}}` 等占位符 | `mock` |

两个 Markdown 文件里的 frontmatter 和 HTML 注释会被自动剥掉，不会送给模型，所以可以放心在里面写维护说明。

访问 <http://localhost:3000/api/config> 的 `prompts` 段可以确认每处装载了多少字、多少个 Skill 配了 `prompt`，避免「改了没生效却不知道」：

```json
"prompts": {
  "systemPrompt":  { "file": "config/system-prompt.md", "chars": 1405, "usedBy": "回复生成（llm）" },
  "intentPrompt":  { "file": "config/intent-prompt.md", "chars": 823,  "usedBy": "意图识别（llm）" },
  "skillPrompts":  { "configured": 12, "total": 12, "usedBy": "回复生成（llm），按命中的 Skill 追加" }
}
```

**全局 System Prompt 与 Skill prompt 怎么分工**：全局写通用约束（不许编造制度、不许泄露他人信息、引用格式）；Skill prompt 写这一类诉求特有的东西。

两个实际生效的例子：

- `it.privileged_access` 的 prompt 要求「制度里提到替代方案就优先推荐」→ 模型回复变成「建议先用数仓脱敏视图或日志平台，可覆盖大部分查询需求」，而不是干巴巴地说需要审批
- `hr.sensitive` 的 prompt 要求「不输出任何具体数字、不追问原因」→ 调薪咨询的回复里不会出现任何薪酬细节

## 从 mock 到真实大模型

### ✅ 已完成：意图识别 + 回复生成

- `src/agent/llm/client.ts` —— OpenAI 兼容客户端：超时、指数退避重试（只重试限流/5xx/超时/网络错误）、错误分类、token 计量
- `src/agent/llm/intent.ts` —— function calling 结构化意图识别 + 三层输出校验
- `src/agent/llm/compose.ts` —— **`config/system-prompt.md` 在这里真正生效**，检索片段与已执行动作作为约束传入

见[双引擎架构](#双引擎架构mock--llm)。

### ⏳ 待做：检索 → 向量库

替换 `src/server/knowledge.ts` 的 `searchKnowledge`。返回的 `Citation[]`（片段 + 来源标识 + 分数）契约不变，前端与 Agent 都不用改。建议保留现在的 TF-IDF 作为混合检索的一路，两路结果做 RRF 融合。

### ⏳ 待做：工具调用改为模型自主编排

目前工具调用由 Skill 配置驱动（确定性）。`config/tool-registry.json` 的结构本来就是照 function schema 设计的，可以直接序列化成 tools 数组交给模型自主编排。

**但这一步要慎重**：让模型自己决定调用顺序会牺牲可审计性。更可能的方向是只把「读取类」工具开放给模型自主调用（查档案、查权限、查知识库），「写入类」工具（建单、建审批）继续由规则驱动。`tool-registry.json` 里的 `sideEffect` 字段就是给这个边界准备的。

### ⏳ 待做：企业系统对接

`src/agent/tools.ts` 里每个工具的执行体从「进程内 Repository 调用」换成「HTTP 调用真实接口」。`tool-registry.json` 里的 `endpoint` 字段就是给这一步准备的。

### ⏳ 待做：数据持久化

`src/server/store.ts` 换成 SQLite / PostgreSQL，`src/server/repositories/*` 的函数签名不变。

### ⏳ 待做：多轮上下文

现在每次请求独立处理，追问后需重述完整诉求。这是目前最影响体验的短板。

## 已知边界

写清楚比藏着好。

| 边界 | 说明 | 后续方向 |
| --- | --- | --- |
| 检索是词面匹配 | 同义改写（"年休假"vs"年假"）依赖 `keywords` 手工覆盖；无 domain 过滤时会被高 IDF 噪声带偏（如"社保从上海转到杭州"命中差旅住宿表里的城市名） | 接 embedding 做混合检索 + rerank |
| 无多轮上下文 | 每次请求独立处理，追问后需重述完整诉求 | 引入会话状态机，把已确认槽位带到下一轮 |
| mock 引擎回复刻板 | 模板拼装，不生成自由文本（换来的是绝不胡说）。切 `AGENT_ENGINE=llm` 即可换成模型生成 | — |
| mock 引擎意图规则手工维护 | 21 个意图靠关键词与正则。`llm` 引擎下退化为意图白名单 + few-shot，不需要写正则 | — |
| LLM 引擎有随机性 | 同一句话两次识别结果可能不同（temperature 已压到 0.2）。风险分级与动作编排不受影响，那部分是确定性的 | 关键场景加样例集打分而非硬断言 |
| LLM 引擎成本与延迟 | 每轮 1~2 次模型调用（级联策略下常见 1 次）。`glm-4.5-air` 实测整轮 2.9~6.3 s；多意图时每个意图各一次合成调用，会线性增加 | 多意图的合成调用并行化；回复合成改流式输出（首字更快）；对固定前缀启用 prompt 缓存 |
| 免费档不可用于交互 | 智谱 Flash 免费档实测 19~27 s 且频繁 429，只适合离线验证 | — |
| 模型会"填补"知识库的空白 | 实测案例：制度表分了「员工/经理/总监」三档但没写 P/M 职级怎么对应，模型自行把 P6 映射成「经理」档，答成 550 元（正确是 400 元）。已补齐制度并在 prompt 里禁止自行推断对应关系 | 这类问题只能靠知识治理发现，是「未命中沉淀 + 人工审核」存在的意义 |
| JSON 文件存储 | 不适合高并发与大数据量（已做写锁与原子写，但仅够 Demo） | 换 SQLite / PostgreSQL，Repository 层已抽象 |
| 无鉴权 | 路由上已按角色分成员工端 / 后台两侧，但**没有强制**：直接访问 `/console/*` 不会被拦。API 也无认证，身份靠前端下拉框模拟 | 加 `middleware.ts` 拦 `/console/*` 校验角色；API 加会话校验与数据行级权限（员工只能看自己的工单，服务台同事按团队看队列） |
| 自由文本槽位不猜 | `reason` / `item` / `city` 这类槽位不做启发式猜测，宁可留空 | 接大模型后由结构化输出补全 |
| 构建期依赖告警 | `npm audit` 有 2 条来自 Next 内置 postcss 的告警，属构建期依赖、不影响运行时；修复需升级到 Next 16 | 跟随 Next 主线升级 |

**部署提示**：可直接部署到 Vercel，但 Serverless 文件系统是只读/临时的，`data/runtime/` 的写入不会持久化（演示够用，重启即回到 seed 状态）。要真正持久化就得换掉存储层。
