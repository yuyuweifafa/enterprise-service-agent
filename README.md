# 企业级员工个人助理 Demo

这是一个面向未来企业的 AI 员工个人助理 Demo。它想表达的不是「再做一个内部工单入口」，而是：**公司所有服务员工的内部部门，最终都可以被收敛到一个 AI 入口里**。

员工不需要知道问题应该找 IT、行政、HR、财务，还是翻哪份制度文档；只需要用自然语言说出目标。AI 助理会结合会议记录、历史文档、知识库、员工个人信息和当前工作上下文，理解员工真正要完成什么，再决定是直接回答、调用工具、推送提醒，还是把上下文交给对应人工部门。

当前 Demo 聚焦一个更清晰的产品定位：**让每个员工都有一个懂自己、懂公司流程、也懂企业服务边界的个人工作助理**。

---

## 产品愿景

未来的企业内部服务不会再是一堆分散入口：OA、IT 工单、行政群、HR 流程、财务系统、知识库、会议纪要、项目文档各自独立存在。员工真正需要的是一个统一入口：它知道你是谁、你正在做什么、你过去参与过哪些会议、相关资料在哪里，以及公司内部有哪些服务能力可以帮你完成目标。

所以这个产品的愿景是：**把企业内部服务入口，从“部门驱动”变成“员工目标驱动”**。

员工只需要说「明天我要和客户评审，帮我准备一下」，系统就应该能理解这不是一句简单问答，而是一个目标：

- 查日程，找到明天可用时间。
- 查会议室，完成或建议预约。
- 读取历史会议记录和项目文档，找出客户关注点。
- 检查相关材料是否齐备。
- 推送联系客户和会前检查提醒。
- 给出天气、着装、心态等个性化建议。

这背后不是单一 RAG，而是「个人上下文 + 企业知识 + 工具能力 + 人工服务」的融合。

这个 Demo 想表达的是：

- 员工侧：从「找入口」变成「说目标」。
- AI 侧：从「回答问题」变成「理解目标、融合上下文、拆解任务」。
- 企业侧：从「多个部门各自提供服务」变成「一个入口统一承接员工需求」。
- 后台侧：从「处理孤立工单」变成「接住 AI 已整理好的员工上下文」。
- 运营侧：从「人工反复回答」变成「把高频问题沉淀进知识库」。

## 设计思路

### 1. 先把“统一入口”做小做深

长期愿景是一个入口承接所有内部服务，但 Demo 阶段不能假装已经接入全部系统。所以当前先收敛成 4 类场景，用较小范围验证完整产品链路：

| 场景 | 说明 |
| --- | --- |
| 闲聊 / 工作陪伴 | 支持员工随口表达、简单情绪安抚、帮忙理清今天要做什么。 |
| 知识库问答 | 回答 VPN、电脑登录、会议室、门禁、报销、年假等制度类问题。 |
| 轻量个人工作助手 | 深做「客户评审准备」一个场景，模拟查日程、约会议室、查资料、推提醒。 |
| 转人工 | 只支持 IT / 行政两个方向，其他 HR / 财务类事项给流程入口，不做人工后台。 |

这样做的原因是：Demo 阶段更重要的是证明「一个入口 + 上下文融合 + 工具调用 + 人工兜底」这条产品链路成立，而不是把所有企业系统都假装接完。

### 2. 个人助理的关键不是聊天，而是理解员工上下文

一个真正有用的企业个人助理，不应该只根据员工刚输入的那句话回答，而是要综合更多上下文：

- 员工档案：部门、岗位、职级、办公地点、直属上级。
- 会议记录：历史会议中客户提过什么问题、后续要准备什么。
- 企业文档：制度、流程、项目资料、客户材料。
- 当前状态：日程、待办、权限、服务进度。
- 服务能力：哪些问题能知识库回答，哪些能调用工具，哪些必须转人工。

当前 Demo 用 mock 数据模拟这些能力，重点展示产品体验：员工感受到的是「它知道我现在要做什么」，而不是「它只是在搜索关键词」。

### 3. 每句话先经过 Agent 判断

员工输入一句话后，系统会先做意图识别，再判断应该进入哪条链路：

1. 如果是普通闲聊，直接由大模型自然回复。
2. 如果是制度类问题，走知识库检索并生成回答。
3. 如果是客户评审准备，拆成日程、会议室、资料、提醒和建议几个步骤。
4. 如果是 IT / 行政问题且知识库无法解决，允许转人工。
5. 如果是 HR / 财务流程类事项，只给「去请假流程」「去报销流程」这类入口。
6. 如果超出服务范围，礼貌说明暂时无法处理。

### 4. 人工不是替 AI 擦屁股，而是接住复杂问题

转人工以后，后台服务人员不是看到一张空工单，而是可以看到：

- 员工原始问题
- AI 的意图判断
- 历史聊天记录
- 员工基础档案
- 会话摘要
- 快捷工作入口
- 是否需要沉淀知识库

这个设计的重点是：人工接入时不需要从头问一遍，AI 先把上下文整理好。

### 5. 知识库不是一次性配置，而是持续运营

当人工处理发现某个问题未来可以标准化回答时，可以在右侧直接沉淀为知识库内容：

- 选择大类
- 填写标题
- 填写标准答案
- 确认沉淀

这个动作对应真实落地里的「知识运营」角色：AI 不是一开始就知道所有问题，而是在服务过程中持续补齐。

## 实际落地价值

### 对员工

- 不用记企业里各种系统入口。
- 不用判断该找 IT、行政、HR 还是财务。
- 不用在会议记录、项目文档、制度文档之间来回翻。
- 常见问题可以即时得到回答。
- 复杂问题转人工时不用重复描述。
- 每个人都能获得基于自身岗位、日程和工作上下文的个性化服务。
- 客户评审这类工作场景可以获得更主动的准备建议，而不是只得到一段通用回答。

### 对服务团队

- 高频重复问题由知识库承接。
- 人工只处理 AI 解决不了的问题。
- 接入人工时已有会话上下文，减少来回沟通。
- 可以追踪哪些问题经常未命中，从而补充知识库。
- IT / 行政可以按部门、人员查看待处理会话。

### 对企业

- 降低内部服务响应成本。
- 提升员工获取服务的体验。
- 把散落在 IM、群聊、制度文档里的服务问题集中到一个入口。
- 把会议记录、企业文档、员工档案和服务流程连接起来，形成更完整的员工工作上下文。
- 形成「提问 - 回答 - 转人工 - 知识沉淀 - 再自动回答」的闭环。

## 当前支持的功能

### 员工端

路由：`/chat`

当前支持：

- 自然语言输入问题
- 闲聊和工作陪伴
- 知识库问答
- 客户评审准备场景
- 模拟查询日程
- 模拟查询和预定会议室
- 模拟读取历史资料
- 模拟推送日程提醒
- 天气和着装建议
- IT / 行政问题转人工
- HR / 财务流程入口按钮
- 人工接入后的双向对话

### 服务后台

路由：`/console/*`

当前支持：

- 查看全部会话记录
- 查看员工与 AI 的历史聊天
- 查看转人工会话
- 按当前处理人查看待处理会话
- 区分 IT / 行政进线
- 人工回复员工
- 结束会话并标记已解决
- 查看员工档案
- 查看会话摘要
- 快捷进入员工档案、知识库、IM 联系等工作入口
- 在人工处理侧沉淀知识库
- 查看知识库文档
- 查看效果数据看板
- 配置能力与服务范围

### Agent 能力

当前 Agent 的核心链路是：

```text
用户输入
  -> 意图识别
  -> 判断服务类型
  -> 知识库检索 / 工具调用 / 自然回复 / 转人工
  -> 生成员工可读的回答
  -> 必要时进入后台人工处理
```

当前模拟能力包括：

- 知识库检索
- 员工档案
- 日程空闲时间
- 会议室查询 / 预定
- 消息 / 日程提醒

## 大模型配置

项目支持真实大模型，也支持本地规则 / mock 能力演示。

如果需要连接智谱或其他 OpenAI 兼容模型，可以在 `.env.local` 中配置：

```bash
AGENT_ENGINE=llm
LLM_BASE_URL=https://open.bigmodel.cn/api/paas/v4
LLM_API_KEY=你的 API Key
LLM_MODEL=glm-4.5-air
```

Demo 中大模型主要负责：

- 理解员工自然语言
- 判断意图和服务范围
- 生成更自然的回复
- 在客户评审准备场景中组织最终回答

工具调用、会议室、日程、提醒等能力目前是 mock 数据，用于展示产品链路。

## 当前边界

这是一个产品 Demo，不是完整生产系统。

当前没有真实接入：

- 企业 OA
- 真实 IM
- 真实 HR 系统
- 真实财务系统
- 真实会议室系统
- 真实日历系统
- 真实权限系统

这些能力在 Demo 中通过 mock 数据模拟，目的是验证产品体验、交互链路和后台协同方式。

如果要走向真实落地，下一步可以补齐：

- 企业身份登录
- 真实知识库接入
- 日历 / 会议室接口
- IM 消息推送
- IT / 行政工单系统
- 知识库发布与审核流程
- 会话数据权限和审计

## 项目定位

这个项目更适合作为「AI 解决方案产品经理 / AI 产品经理」作品集 Demo，而不是单纯前端作品。

它想证明的不是页面有多少，而是：

- 能不能把一个企业内部服务场景拆清楚。
- 能不能判断哪些适合 AI 自动处理，哪些必须交给人。
- 能不能设计员工端、后台端和知识运营的闭环。
- 能不能把大模型能力、知识库、工具调用和人工协同放进同一个产品链路里。
